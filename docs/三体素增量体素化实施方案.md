# 三体素增量体素化实施方案

> 状态：设计方案，尚未实施。本文描述的是建议的目标架构，不代表当前代码已经采用该流程。主要性能目标是 50ms 窗口（20 个窗口/秒）。

## 1. 目标

将当前关键路径：

```text
收集完整时间窗口
→ CPU拼接为完整 NumPy 事件数组
→ 集中上传 GPU
→ GPU 构建 15-bin 体素
→ E2FAI 推理
```

改为：

```text
事件按微批次到达
→ 根据固定窗口时间立即计算时间 bin
→ 异步上传 GPU
→ 增量累加到当前体素
→ 窗口结束时封存体素
→ E2FAI 推理
```

窗口结束后不再重新构建体素。窗口结束操作只负责等待已提交的 GPU 累加完成，然后将体素交给模型。

## 2. 事件如何增量放入体素

这里的“放入体素”不是只放入时间，而是每条完整事件：

```text
x, y, timestamp, polarity
```

对于已知的固定窗口：

```text
window_start_ns
window_end_ns = window_start_ns + window_ns
```

事件的连续时间坐标为：

```text
t = (event_time - window_start_ns) / window_ns × (NUM_BINS - 1)
```

当 `NUM_BINS = 15` 时，时间坐标范围为 `0～14`。每条事件根据 `t` 线性累加到相邻时间 bin：

```text
b0 = floor(t)
b1 = b0 + 1
fraction = t - b0
sign = +1 (ON) or -1 (OFF)

voxel[b0, y, x] += sign × (1 - fraction)
voxel[b1, y, x] += sign × fraction
```

窗口使用半开区间：

```text
[window_start_ns, window_end_ns)
```

时间恰好等于 `window_end_ns` 的事件归入下一个窗口。

## 3. 为什么需要固定窗口归一化

当前实现使用实际首尾事件：

```text
(event_time - first_event_time)
/
(last_event_time - first_event_time)
```

窗口未结束时，`last_event_time` 会持续变化，先前事件所属的 bin 也会随之变化，因此无法精确增量填充最终体素。

固定窗口的起止时间从窗口开始时就已知，事件到达后可以立即确定 bin。这是实现精确增量体素化的前提。

## 4. 三体素池

预分配三个 GPU `float32` 体素，每个形状为：

```text
[1, 15, processing_height, processing_width]
```

每个槽位保存：

```text
voxel
window_id
window_start_ns
window_end_ns
generation
event_count
state
fill_done_event
inference_done_event
```

槽位状态：

```text
FREE         空闲
CLEARING     GPU正在清零
FILLING      正在接收并累加事件
READY        窗口已结束，等待推理
INFERENCING  模型正在读取
```

典型使用状态：

```text
体素A：推理窗口N
体素B：等待推理窗口N+1
体素C：填充窗口N+2
```

E2FAI 推理仍严格按窗口顺序执行，因为后一窗口需要前一窗口的 GRU 状态。可以并行的是“当前窗口推理”与“后续窗口体素填充”。

## 5. 时间线示例

以 50ms 窗口为例：

```text
0～50ms
  A填充窗口1

50～100ms
  A推理窗口1
  B填充窗口2

100～150ms
  B推理窗口2（若A已完成）
  C填充窗口3
  A清零后备用

150～200ms
  C推理窗口3
  A填充窗口4
  B清零后备用
```

第三个体素主要吸收短时推理抖动。如果平均推理时间长期大于窗口长度，任何有限数量的体素缓冲最终都会被占满。

## 6. 微批次与异步上传

不建议每个很小的相机包都单独启动一次 CUDA 操作。收到事件后，先在预分配的 CPU 固定页内存中构成微批次。

面向 50ms 主要工作窗口，初始默认值为：

```text
microbatch_max_events = 65536
microbatch_max_wait_ms = 2
```

满足任一条件时立即提交：

```text
第一条尚未提交的事件已等待 2ms
或达到设定事件数量
或到达窗口边界
```

50ms 窗口按 2ms 最长等待计算，每窗口最多约有 25 次按时间触发的提交；高事件率下还可能由事件数量阈值提前触发。微批次数量与 15 个时间 bin 没有一一对应关系。

微批次保存：

```text
x: int32
y: int32
timestamp: int64
polarity: uint8
```

至少使用两个固定页暂存槽，防止前一批尚未上传完成就被 CPU 覆盖。上传使用 `non_blocking=True` 并在专用 CUDA stream 中执行体素累加。

## 7. CUDA 同步模型

使用两条主要 CUDA stream：

```text
voxel_stream
  - 异步上传微批次
  - 增量体素累加
  - 体素清零

inference_stream
  - E2FAI模型推理
  - 输出复制
```

窗口结束时：

```text
voxel_stream 记录 fill_done_event
→ inference_stream 等待 fill_done_event
→ 模型读取完整体素
```

推理结束时：

```text
inference_stream 记录 inference_done_event
→ voxel_stream 等待 inference_done_event
→ 该槽位才可以清零和复用
```

## 8. 现有队列的去留

### C++ Bridge 发送队列

保留。它位于 CPU，保存尚未通过 TCP 发送的原始事件批，用于吸收网络短时阻塞。当前上限为 32 批/256MiB。

当启用实时新鲜度策略时，Bridge 允许丢弃未发送的旧批次追赶最新数据。当启用“仅 4GiB 容量上限”的顺序模式时，Bridge 不得在自身队列满时丢弃旧批次，必须改为背压等待，否则即使 Worker 不丢数据，上游仍然会丢失。

### Worker 事件队列

保留。它位于 CPU，保存已收到但尚未提交 GPU 的原始事件批，用于解耦 TCP 接收线程和 GPU 提交线程。它是安全缓冲，不是体素缓冲。

队列的 4GiB 指原始事件 payload 字节上限，不等于 Python Worker 整个进程的 RSS 内存上限。NumPy 对象、元数据、微批次固定页缓冲和模型内存不包含在这 4GiB 中。

### EventWindowBuffer

改为轻量窗口路由器，负责：

```text
识别事件所属窗口
在窗口边界分割跨窗口事件包
生成微批次
记录窗口元数据
```

它不再保存并拼接整个窗口的全部事件。

### 结果队列

保留容量为 1 的结果队列，让 GPU 推理与 CPU 图像编码、TCP 发送解耦。

## 9. 队列与三体素的两种运行模式

### 9.1 实时新鲜度模式

如果出现：

```text
A正在推理
B等待推理
C已填满
新窗口继续到达
```

采用以新鲜度为优先的恢复策略：

1. 不覆盖正在推理的体素。
2. 增加 `processing_generation`，使旧结果自动失效。
3. 丢弃尚未推理的旧 `READY` 体素。
4. 清理过旧的 CPU 事件队列和窗口残留。
5. 保留最新事件，重新选择体素填充。
6. 下一次推理使用 `state = None` 重置 GRU。

新鲜度原则：

```text
积压超过 600ms 触发追赶
清理后保留不超过 300ms 的最新数据
```

在 50ms 主要窗口下，600ms 约等于 12 个窗口，300ms 约等于 6 个窗口。

### 9.2 无新鲜度、4GiB 容量上限的顺序模式

该模式的目标是优先保留到达 Worker 的事件顺序，允许延迟随积压增长，不根据数据年龄丢弃旧事件或旧窗口。

```text
freshness_enabled = false
queue_policy = ordered
worker_event_payload_limit = 4GiB
```

在此模式下：

1. 不执行 600ms 触发和 300ms 目标清理。
2. 不在 1.5GiB 等提前阈值主动丢弃事件。
3. 不因常规批次数量达到 256 就提前清理；4GiB payload 是主要容量上限。
4. 三个体素全部占用时，不丢弃 `READY` 体素，后续原始事件留在 CPU FIFO 中等待。
5. 模型按 `window_id` 严格处理所有已接受窗口，不因结果已经过时就重置 GRU。
6. GUI 必须显示“顺序积压”状态，包括队列字节数、最旧数据年龄和预计清空时间，不能将延迟结果表示为实时。

三体素在这种模式中只保存最多三个已路由窗口；其余积压以原始事件形式保存在 4GiB CPU 队列中，避免无限增加显存。

#### 4GiB 可以保存多少事件

当前线上每条事件的 payload 为 13 字节，4GiB 约可保存 3.30 亿条事件。可吸收的积压时间取决于实际事件率：

| 事件率 | 4GiB 约对应的原始事件时间 |
|---:|---:|
| 1M events/s | 330s |
| 5M events/s | 66s |
| 10M events/s | 33s |
| 20M events/s | 16.5s |
| 50M events/s | 6.6s |
| 100M events/s | 3.3s |

这些是只按 13 字节 payload 计算的理论值，不是总内存占用保证。

#### 到达 4GiB 时的行为

不使用新鲜度意味着不应在到达上限后悄悄删除最旧数据。建议使用有界背压：

```text
高水位：4GiB，停止从TCP继续读取新payload
低水位：3GiB，队列消耗到该值后恢复读取
```

新事件批必须整批入队，不能只放入部分事件。为确保单个在途包也不使 Worker payload 超过 4GiB，接收协议需要先解析包头长度，有足够剩余容量时才读取 payload；或者为最大单包预留容量。

Worker 停止读取后，TCP 背压会逐级传递到 Bridge。Bridge 在顺序模式下也必须等待队列空间，不得执行旧批删除。

需要明确的物理限制：如果实时相机不能被背压或暂停，且事件长期产生得比模型处理更快，那么任何有限内存都无法保证永不丢失。上游 ROS 或驱动缓冲最终可能溢出；系统必须检测序号/时间戳断流，明确记录丢失并重置 GRU。若要在无法暂停的实时源上保证不丢数据，需要增加磁盘落盘队列或先录制后离线处理，这不在本三体素方案的内存上限范围内。

#### 当前行为与目标行为的差异

当前 `--no-freshness` 只关闭按等待时间触发的追赶，并不会自动得到本节描述的顺序模式：

- 容量追赶仍可能提前触发。
- 当前还有 256 批的数量上限。
- 即使关闭主动追赶，到达硬上限后仍会丢弃旧批。
- Bridge 当前在自身队列溢出时仍会删除旧批，尚未按 `catchup_enabled=false` 切换为背压。

因此实施时应使用明确的 `queue_policy=realtime|ordered` 取代多个容易组合出模糊语义的布尔开关。

## 10. 参数切换

GUI 修改时间窗口或处理分辨率时：

```text
停止当前会话接收
→ 增加generation
→ 清空CPU事件队列
→ 等待正在执行的CUDA操作安全结束
→ 按新分辨率重建三体素池
→ 重置GRU状态和窗口边界
→ 启动新会话
```

窗口长度变化时同步更新：

```text

时间bin换算比例
窗口边界
flow_max_px
积压与新鲜度统计
```

光流预览范围：

```text
50ms  → 10px
100ms → 20px
150ms → 30px
200ms → 40px
250ms → 50px
```

## 12. 行为变化与兼容模式

固定窗口归一化会保留窗口前后的静默，不再将实际事件时间跨度强制拉满 15 个 bin。这会改变预训练模型的输入分布，尤其会影响稀疏事件和短时运动。

实施时应保留两种模式：

```text
event_span    当前首尾事件归一化，用于对照和回退
fixed_window  固定窗口归一化，支持增量体素化
```

`event_span` 模式可以提前上传原始事件，但仍需等待窗口结束后才能确定最终 bin。`fixed_window` 模式才能精确地边接收边构建最终体素。

## 13. 建议代码拆分

### `runtime/nrv_e2fai/preprocessing.py`

- 保留一次性固定窗口体素化作为正确性基准。
- 将当前 `EventWindowBuffer` 拆分为窗口路由、断流检测和元数据构建。

### `runtime/nrv_e2fai/incremental_voxelizer.py`

- 管理三体素池。
- 管理固定页微批次缓冲。
- 管理 CUDA stream/event。
- 提供 `append()`、`finish_window()`、`acquire_ready()` 和 `release()` 接口。

### `examples/e2fai_worker.py`

- 将收到的事件包路由到相应窗口。
- 提交微批次而不再等待完整窗口拼接。
- 按 `window_id` 顺序执行模型。
- 处理体素池耗尽、generation 变化和 GRU 重置。
- 增加 `queue_policy=realtime|ordered`，将新鲜度追赶与 4GiB 顺序背压的语义彻底分开。
- `ordered` 模式不使用 256 批次作为常规容量触发器，并在 4GiB/3GiB 高低水位之间施加背压。

### `ros_ws/src/nrv_demo/src/e2fai_bridge.cpp`

- 使 `catchup_enabled=false` 或 `queue_policy=ordered` 真正禁止 Bridge 容量追赶和旧批删除。
- Bridge 队列达到自身上限时通过条件变量等待发送空间，并显示 `backpressured` 状态。
- 保留序号缺口、未发送字节和背压时长统计。

### `ros_ws/src/nrv_demo/scripts/e2fai_protocol.py`

- 若要严格确保 Worker 的排队 payload 不超过 4GiB，需将包头解析与 payload 读取拆开，在读取 payload 前预留队列容量。

### `scripts/run.sh` 与 launch 文件

- 对外提供单一明确参数：`E2FAI_QUEUE_POLICY=realtime|ordered`。
- `ordered` 自动配置 Worker 和 Bridge，避免只关闭一端的追赶。
- 记录每次运行的队列策略、字节上限和高低水位。

## 14. 验证标准

### 正确性

- 相同事件的一次性固定窗口体素化与分批增量体素化结果在浮点容差内一致。
- 任意改变事件包分割位置不改变最终体素。
- 窗口边界、ON/OFF 极性、空窗口和时间戳断流行为正确。
- 分辨率或窗口切换后不沿用旧体素和旧 GRU 状态。

### 并发安全

- 推理中的体素不会被清零或覆盖。
- 异步上传完成前固定页暂存区不会复用。
- 推理顺序严格按 `window_id` 递增。
- 恢复后的旧 generation 结果不会进入 GUI。

### 4GiB 顺序模式

- 关闭新鲜度后，不会在 600ms/300ms 阈值丢弃数据。
- Worker 队列不会在 1.5GiB 或 256 批时提前追赶。
- 三体素全部占用时，后续事件保留在 CPU FIFO，已就绪体素不被删除。
- Worker 在 4GiB 停止读取，下降到 3GiB 后恢复，新事件批不会被部分入队。
- Bridge 在顺序模式下使用背压而非删除旧批。
- 分别模拟 1M、10M、50M events/s，验证 4GiB 容量和队列年龄统计。
- 模拟上游无法背压时的序号缺口，验证明确报告丢失并重置 GRU，不会误报为无损运行。
