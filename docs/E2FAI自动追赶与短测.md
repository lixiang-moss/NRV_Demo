# E2FAI 自动追赶与必要短测

日期：2026-09-12。基于 main 的 `ef05fd8` 修改。本次实现用户确认的新鲜度方案，替代“过载后暂停到手动重启”。未进行真机录制、长测或新的性能对照。

## 生效规则

| 项目 | 默认设置 |
| --- | --- |
| 宿主事件 FIFO 容量触发线 | 入队后预计达到 1 GiB = 1024 MiB |
| 宿主事件 FIFO 硬上限 | 2 GiB = 2048 MiB |
| 追赶后容量目标 | ≤512 MiB |
| 批次保护 | 预计达到 256 批时，清理至最多 128 批 |
| 新鲜度 | 默认开启，等待超过 500 ms 触发；清理至 ≤250 ms |
| 模型组窗 | 250 ms 半开区间，正常收集不算积压 |
| 真实事件断流 | 仍为超过 300 ms，与等待超限分开处理 |

容量或新鲜度任一触发，都从最旧端删除完整批次，保留最新连续后缀，同时满足容量、批次和等待目标。单批不能满足目标时整批跳过；不会随机抽事件、排序或修改时间戳。检查发生在插入之前，也发生在推理线程取批次之前。FIFO 不会先突破 2 GiB 再清理。

追赶时作废已组好的旧窗口，清理受影响半窗，从保留数据重新收集完整窗口；增加处理代号，清空 ConvGRU，并让结果线程重置灰度归一化状态。尚未领取新代号数据期间的连续清理合并为一次重置。旧 GPU 工作可以完成，但其结果在交接、转图后及发送前检查代号并取消。已经开始传输的 TCP 包保持完整；接收端和 GUI 也检查代号，获知新代号后拒绝旧结果。已在追赶通知前显示的画面无法撤回。

接收、相机与原图持续运行；GUI 状态显示“正在追赶”，第一幅有效新结果后恢复 connected。没有足够新事件时等待输入，不制造空窗口、不重新加载权重。真正的模型非有限值或协议错误仍报告错误。

C++ 发送队列保留 32 批 / 256 MiB 上限。满时清理尚未发送的旧批次，向半水位清理，至少保留能装下的最新一批；正在传输的包不截断。后续事件包携带桥接恢复代号，宿主清理该断点以前的队列和循环状态。组窗缓存超限同样转为跳过和恢复。

## 时间和接口口径

- 未组窗批次：`CLOCK_MONOTONIC 当前时间 − C++ 桥 callback_ns`，包括桥内转换、发送等待、TCP 传输和宿主排队；刚从 TCP 收到的旧包不会被当作新数据。
- 完整待推理窗口：从补齐输入的批次在宿主完整接收时计时，结果元数据记录 `input_complete_ns`，测量项为 `complete_window_wait`。不从窗口第一个事件开始计时。
- 宿主和 Docker 的时间命名空间偏移均为 0，使用同一 Linux 内核的单调时钟，见[检查记录](validation/catchup_20260912/clock_offsets.txt)。事件映射时间未用于新鲜度判定，也未修改。
- 500 ms 约束待处理等待，**不是相机到屏幕的延迟保证**。2 GiB 仅限制宿主队列负载，不包括正在接收的包、组窗数组、模型、结果、ROS 缓冲与显存。
- `/dvs/events` 和每事件 13 字节字段保持不变；NEF1 帧头和图像负载保持不变，新增 `status` 控制包及代号元数据。`E2faiResult.msg` 新增 `processing_generation`，用于 ROS/GUI 的旧结果隔离；因此须同步重建镜像和外部结果订阅程序。当前 ROS 镜像已重建。

`catchup_*` 统计主动丢弃的批次、事件、字节、半窗、完整窗口、旧推理及旧结果。它们不是同一粒度，不应简单相加为一个“丢帧数”。原 `raw_sequence_gaps` 仍表示 RAW 序号间断次数。模型在主动跳过处重新建立 ROS 批次连续性基点，不把自己丢弃的批次计入上游丢包；跳过区间内是否另有上游间断，需看 RAW/适配器记录。

`integration_summary.json` 发生追赶时标为 `DEGRADED`，表示输入有主动损失；不会因此报告会话错误或停止演示。性能开关仍默认关闭，开启时周期记录追赶和等待测量，无逐事件打印。

## 必要短测结果

后续按用户要求将新鲜度触发阈值放宽到 500 ms，清理目标同步为 250 ms；本次参数修改未运行测试。以下测试记录仍对应修改前的阈值。

以下为最初 512 MiB 触发、1 GiB 硬上限配置的软件短测历史，**不是新版本真机性能结果**。不据此宣称 FPS 或实际显示延迟改善。当前容量已按用户要求增大为上表设置，原日志不作改写。

| 检查 | 结果与证据 |
| --- | --- |
| 宿主队列和会话 | 22 项通过，约 1.5 秒；覆盖 512→256 MiB、1 GiB 拒绝边界、256→128 批、回调年龄、整批有序丢弃、重置合并、GPU 前向阻塞模拟、旧结果失效、发送阻塞与 Stop。容量边界用字节账本验证，没有分配 1 GiB 测试数据。[日志](validation/catchup_20260912/worker.log) |

## 启动与复测

从工程根目录执行；默认开启，无须添加参数：

```bash
./scripts/run.sh

# 只关闭等待时间控制，容量超限仍自动追赶
E2FAI_FRESHNESS=false ./scripts/run.sh

# 需要记录下一次真实运行时使用
PERF_ENABLED=true ./scripts/run.sh

# 必要的软件短测
PYTHONNOUSERSITE=1 ~/miniconda3/envs/nrv-e2fai/bin/python -m unittest discover -s tests -p test_e2fai_worker.py -v
NRV_TEST_CPP_BRIDGE=1 python3 -m unittest discover -s tests -p test_e2fai_cpp_bridge.py -v
docker run --rm --network none -e QT_QPA_PLATFORM=offscreen -v "$PWD:/workspace:ro" nrv-demo:noetic python3 -m unittest discover -s /workspace/tests -p test_gui_views.py -v
```

本次软件短测只确认追赶机制与状态隔离能正确工作。高负载下能保留多少窗口、是否连续追赶、画面是否足够流畅，仍需下一次真机短记录确认；不以更大的队列或本次模拟输入替代这项证据。
