# E2FAI 演示性能优化实施方案

2026-09-12 | 基于现有代码与原始统计独立复核 | 仅方案，未执行优化

## 1. 推荐决策

短期演示采用这一顺序：修正出图定时和参数读取；处理事件时间异常；先试原生分辨率混合精度，再把 CPU 转图与发送移出推理串行路径；若 ROS 接收仍丢批次，用 C++ 替换桥；若模型仍达不到所需速度，再选择 640×480 推理或明确的演示跳窗模式。

线程、进程、C++ 和推理引擎都可以用，选择依据是哪个资源阻塞了下一步。本方案重新读取代码和 metrics.csv，没有沿用旧优化方案作为依据，也没有新增运行测试。以下性能目标均为建议验收线，不是已取得的提升。

## 2. 三个问题的直接答案

### GPU 前向是什么

正确术语是“前向计算”：把一个事件窗口构造成 15-bin 体素，再让模型计算灰度重建、光流和下一步循环状态。它就是推理中的模型计算，不是训练或 GPU 绘制窗口。

当前 forward_step 包含 U-Net、光流池化与插值、ConvGRU 和图像残差。冻结主干只停止更新权重，前向仍要执行。调用已使用 inference_mode，不能再把“关闭梯度”当成尚未做的优化。

GPU 前向中位数 120.83 ms，已经大于 100 ms 窗口周期。只计算这一项的理想吞吐上限约 8.3 窗/秒，完整串行链路还会更低；这不是实测容量。实测约 2.25 个结果/秒还混合了输入间断、状态重置和其他阶段的影响。

### Python 绘图为什么慢，能替换什么

这里不是 Matplotlib，而是 NumPy 画布加 OpenCV 的十字、圆和六次 putText 调用。draw 指标是这段代码的墙钟时间，包含线程抢占、GIL 等待等可能的影响；现有数据不能证明 36 ms 都在实际画字。C/C++ 扩展可能释放 GIL，但回到 Python 时仍需重新取得它。[Python 线程说明](https://docs.python.org/3.10/library/threading.html)

比直接替换 OpenCV 更明确的问题是：主循环先取 ROS 参数、生成图像，最后无条件 sleep(0.1)。实际周期是“工作时间 + 100 ms”。即使绘图只需 20 ms，也只能约 8.3 FPS。当前取参数和完整出图均值约 14 ms、51 ms，量级上已能解释为什么设 10 FPS 却只有约 5.6 FPS，不能据此精确归因全部差额。

优先修正定时、缓存参数；仍受 Python 调度影响时，把图像合成放进独立进程或 C++。只给同一 Python 进程增加画字线程，不能保证解决问题。

### 宿主 FIFO 排队是什么

FIFO 是先进先出队列。宿主机是运行 GPU 模型的本机系统。现有接收线程不断把 TCP 事件批放入队列，另一个消费者依次取出事件批、组窗、体素化、推理、转图、发送结果。这个队列装的是事件批，不是固定数量的完整窗口。

消费者推理时，接收线程仍在入队。消费者随后还要等 CPU 转图和同步发送，期间不再取下一批；一个事件批产生多个完整窗口时，这段停顿还会延长。因此排队是串行工作造成的现象，不能直接归罪于“队列实现慢”。

FIFO 等待中位数只有 5.50 ms，但 P95 达到 164.01 ms，符合“很多批次很快被取走，另一些撞上推理忙碌期”的现象。组窗自身 P95 仅 0.56 ms。空队列时还有最多约 10 ms 的轮询等待，可用条件变量唤醒消除；它解释不了 164 ms 的尾部。

## 3. 采用的证据及解释边界

同一 RAW、原生 960×720、100 ms 窗口、软件过滤关闭；四画面开启测量的一次 60 秒有效统计。宿主为 RTX 3060，PyTorch 2.1.1 / CUDA 12.1。

| 阶段 | P50 / P95，ms | 统计单位 | 对方案的意义 |
| --- | ---: | --- | --- |
| 原支路完整出图 | 48.49 / 103.99 | 334 次出图 | 定时之外还有较大的工作段 |
| 原支路绘图段 | 36.25 / 89.73 | 334 次出图 | 需区分实际 CPU 与调度等待 |
| 每轮读取参数 | 10.68 / 37.24 | 333 次读取 | 不适合放在每帧关键路径 |
| 宿主 FIFO 等待 | 5.50 / 164.01 | 1,801 个事件批 | 消费者存在较长忙碌期 |
| GPU 前向 | 120.83 / 122.99 | 134 个窗口 | 10 窗/秒的明确计算障碍 |
| 模型结果转图打包 | 23.57 / 25.82 | 134 个窗口 | 可以与后续推理重叠的 CPU 工作 |
| 模型结果发送 | 11.91 / 35.36 | 134 个窗口 | 不能一直阻塞推理消费者 |
| GUI 接收到刷新 | 48.79 / 94.47 | 1,135 幅图像 | 100 ms 定时器引入显示等待 |
| GUI 转换缩放提交 | 1.11 / 2.42 | 1,135 幅图像 | 暂无必要优先重写 GPU 显示 |

这些行不可直接相加为端到端分位数；draw 包含于完整出图，CPU 等待 GPU 输出与 GPU 前向也重叠。原支路画布锁等待 P95 约 0.003 ms，目前不应把精力放在复杂无锁算法上。

无 GUI、1/2/4 画面时模型结果率约 2.24 / 2.22 / 2.34 / 2.25 FPS，没有证据表明减少窗口能解决主要瓶颈。GPU 平均利用率约 30.5% 是采样均值，包含输入等待，不能用它证明模型前向没有计算瓶颈。

另有独立问题：约 20 秒真机运行产生 36 个结果和 69 次状态重置；时间审计发现约 4,295 秒的事件时间正跳。ROS 序号间断已观察到，但回调前反序列化、传输和 ROS 排队还未分别归因。修复输入后，模型收到的有效窗口可能更多，负载反而会上升。

## 4. 第一批改动：少量代码即可尝试

### A. 出图使用固定期限，参数离开逐帧路径

修改 demo.py 的 run（当前 188-217 行）：每次期限递增 100 ms，只等待剩余时间；工作超时就进入下一个未来期限，记录一次迟到，不补画一串旧图。期限使用 monotonic，避免系统时间校正影响刷新。

将 get_param 改为初始化读取，加独立低频读取任务，例如 5 Hz；读取后原子替换完整配置快照。保持 GUI Apply / Load 最多约 200 ms 生效。若必须立即生效，再接已有 Apply 路径触发配置更新，不新建复杂配置系统。配置只在事件批边界应用，过滤历史按原规则保留。

收益方向：提高原算法出图节奏，去掉逐帧参数服务等待。显示统计窗口会由“工作 + 100 ms”缩短到接近 100 ms，所以每幅图的事件数、质心可能变化；过滤规则和总事件计数不变。这是必须说明的行为变化。

### B. 模型输出只复制一次光流，先试混合精度

worker 的 render_result 先把 GPU 光流转到 CPU 生成 HSV，又再次转到 CPU 生成浮点光流。改为一次下载 float32 光流，同一个数组供 HSV 和 32FC2 打包使用。保留位序、通道、数值和整幅尺寸，预计减少复制，收益需短测。

保留 eval / inference_mode，在模型调用外启用 FP16 autocast，不把所有输入和权重盲目 half。输出继续转换为 float32；首先保持 GRU 的状态更新与敏感归约使用 FP32，若误差仍大，就只对 U-Net 使用 autocast。需要在模型内部划分精度区段，单纯对最终输出 float() 不能修复此前已经产生的误差。[PyTorch AMP](https://docs.pytorch.org/docs/2.14/amp.html)

固定分辨率下单独尝试 channels_last、cuDNN benchmark；前者可能因不支持的算子发生格式转换，后者增加启动搜索且可能影响可重复性，均不能预设必然提速。[内存格式说明](https://docs.pytorch.org/tutorials/intermediate/memory_format_tutorial.html)、[cuDNN 搜索说明](https://docs.pytorch.org/docs/2.14/notes/randomness.html)

外部说明使用当前官方文档；本机 2.1.1 已核对存在 torch.cuda.amp.autocast，实施采用本机接口，不为此升级整个环境。先做单项比较，不一次把所有开关打开。

### C. GUI 在新图到达时合并刷新请求

保留最新图像缓存；ROS 接收线程只更新缓存并通过 queued signal 通知 Qt。已有刷新请求时不重复排队；Qt 主线程取最新图像并提交。控件操作仍只在 Qt 主线程进行。这样可以消除许多“已经收到图，仍等下一次 100 ms 定时器”的等待。

保留低频状态定时器，不对没变的图片重复缩放。预计改善的是显示等待，不是模型推理速度；不要把刷新定时器提高到 60 Hz 冒充模型达到 60 FPS。

## 5. 第二批改动：把 CPU 与 GPU 真正重叠起来

### 推荐结构

容器侧保持 ROS / Qt。宿主侧保持一个拥有 CUDA 和 ConvGRU 状态的进程，增加一个只处理 CPU 图像的子进程；子进程用 spawn 启动，不继承 CUDA 上下文。现有 TCP 接收线程继续使用，再增加一个顺序组窗线程；结果发送由 CPU 子进程中的 I/O 线程处理。

```text
容器事件桥 -> TCP 接收线程 -> 顺序组窗线程
                                  |
                             完整窗口队列
                                  |
                          单一 GPU 推理消费者
                                  |
                      CPU 输出快照 / 有界缓冲
                                  |
                    CPU 转图进程 -> 发送线程 -> ROS -> Qt
```

组窗是 CPU 数组工作，可以与 GPU 推理重叠；体素构建当前使用 GPU，先仍放在 GPU 消费者内，不把它当作已经实现的 CPU 预处理。推理窗口和 state 保持严格顺序。n 窗口推理结束并保存 state 后，n 窗口转图、发送可以与 n+1 窗口推理重叠。

输出用两个预分配 CPU 槽先实现流水化，发布槽编号和元数据，消费者完成后归还槽。只传 NumPy / CPU 数据；不要把大图装进普通 multiprocessing.Queue 后任由 pickle 复制。初版可同步完成一次 GPU 到 CPU 下载，再交给后处理；确有收益后才引入 pinned memory、异步拷贝、CUDA event 和槽位复用保护。

接收原始批队列保留字节上限；新完整窗口队列初值 2 个窗口，输出槽 2 个。这些是方案起点，不是性能调优后的容量。必须记录原始队列、完整窗队列、处理中窗口、输出槽的合计年龄，不能把积压从 FIFO 移到其他队列后宣称改善。

### 状态与输出顺序

每项携带 session、generation、window_id。重启、时间异常、跳窗会推进 generation；清理旧队列；正在计算的旧结果不能发布。GPU 单一消费者负责 GRU state，CPU 转图单一消费者负责 RunningRange，不能多个线程同时修改它们。

兼容模式下每个推理结果都转图并按序发送，输出满则背压，持续超载仍显式报错。展示图允许只留最新时，也应先决定是否让 RunningRange 观察所有结果；否则跳过 CPU 转图也会改变后续灰度亮度。浮点算法结果是否丢弃应独立配置，不能默默随着预览图丢弃。

### 哪些并行值得做

| 方法 | 本项目取舍 |
| --- | --- |
| 接收 / 发送用线程 | 推荐，适合 I/O；现有接收和桥发送已经用了线程 |
| CPU 转图独立进程 | 推荐候选，隔离 Python 调度，与下一窗 GPU 计算重叠 |
| 同一进程增加很多 Python 绘图线程 | 不优先；GIL 和共享画布可能让收益很小 |
| 相邻窗口多线程并发执行完整模型 | 不直接采用；下一窗 ConvGRU 需要上一窗状态 |
| 拆 U-Net 无状态部分，再顺序执行 GRU | 技术上可行；单 GPU 未必变快，先不承担拆分复杂度 |
| 相邻窗口 U-Net 小批量推理 | 可提高吞吐，但等待凑批增加延迟，GRU 仍须逐窗执行 |
| 双 GPU / 多进程复制完整模型 | 独立相机流更合适；同一循环序列不能随意分给两个模型 |

流水化改善的是重叠和 GPU 空闲时间。若前向仍约 121 ms，再多线程也不能让这个串行模型完整处理每秒 10 个窗口，必须配合模型加速、改变窗口周期或跳窗。

## 6. Python 绘图与 ROS 接收的替代方案

### 低改动：独立合成进程，保留现有图像话题

原事件回调仍按顺序过滤和累积，刷新期限到达时原子取走画布与 count / sum / stamp 快照，交给独立合成进程画十字、圆和文字并发布原图像话题。静态标题预生成；动态文字值没变就复用，不强制降低动态数值更新频率。

可先用每幅约 2.07 MB 的有界单帧复制实现，再看是否值得做双缓冲；若直接用双缓冲，读者归还前不可清空或复用。当前锁等待很小，所以双缓冲不是第一优先级。画布交换、计数归零和时间戳必须属于同一快照。

### 更彻底：C++ 原支路与桥

ROS 桥先换成 C++ 订阅 EventArray，逐字段写入当前 TCP 协议，保留整数纳秒、事件顺序和批次追踪，避开 Python 逐事件对象访问。若仍有额外复制压力，再让 C++ 适配器直接输出紧凑事件数组给新支路，原 /dvs/events 继续保留兼容。

原过滤与质心也可以迁到 C++ nodelet，直接处理解码后的批数组并用 OpenCV 合成图像。这条路线能一起减少 Python ROS 反序列化和对象转数组成本，但必须保持跨批过滤历史、同像素 ON/OFF 覆盖规则和统计含义。只搬绘图、不搬慢的接收路径，不能保证治好 ROS 序号间断。

### 仅用于演示的界面叠加

事件图作为底图；计数用 QLabel，十字 / 圆用 QPainter 覆盖在显示图上，使用与图像相同的缩放比例和留白偏移。这可以省掉每帧把文字烧进全分辨率图像的步骤。

代价是原发布图像、截图或下游不再天然包含这些标注。若需要保持原接口，就保留后台合成并发布的路径。官方 renderer 没有自动继承 Python 软件过滤，不能直接替换过滤支路后声称效果不变。现有 GUI 提交很快，没有依据优先换成 OpenGL / CUDA 绘图。

## 7. 时间异常与过载，给出可执行的选择

### 时间异常：优先修正确认的解码原因

检查 adapter 的 setTimeMultiplier(1000)、decoder 时间单位、高低位拼接、溢出展开状态以及 factory 实例是否跨包保留。已观察到的约 2^32 微秒跳变是线索，不足以断言某一行代码就是根因。用现有 RAW 中包含一次异常的短片段，记录异常前后原始时间字与解码 sensor_time，确认后在解码适配层修复。

若短期内无法修复，演示可显式切到“模型近似时间”：保留原始事件时间字段，为模型单独生成基于可靠包头的插值时间并在组窗、体素化两处一致使用。包头重复、倒退、断流时另开 generation。必须显示“近似时间”标记，不能只改组窗、不改体素时间，也不能用它宣称精确传感器延迟。这是兼容性改变和应急选项，不是默认偷偷回退。

### 容量不足时，只能三选一

| 选择 | 做法 | 代价 |
| --- | --- | --- |
| 完整输入、100 ms 窗口 | 加速消费者直到平均服务能力超过到达率 | 对 GPU 与入口性能要求最高 |
| 完整输入、更长窗口 | 例如先试 200 ms，目标 5 窗/秒 | 时间细节降低；事件密度及光流每窗含义改变 |
| 演示优先、允许跳窗 | 保持 100 ms，超龄时跳到最新完整窗 | 丢失时间段；需重置循环状态 |

建议演示跳窗初值：按共享单调时钟计算，从最后贡献批进入桥回调开始，若窗口尚未开始推理且已超过 200 ms，就丢弃过期完整窗并选最新完整窗。这个时钟只覆盖已观察链路，不含 ROS 回调前积压，更不是物理采集延迟；必须同时监控上游序号与接收情况。

保留最新未完成窗，清掉更旧的待处理原始批 / 完整窗，严格按 generation 重置 GRU 与显示归一化。当前 GPU 核函数不强行中断，旧 generation 结果完成后拒收。跳过的原始事件段、窗口数和原因应随结果报告。下游不允许丢浮点结果时，不能用这一模式替代兼容模式。

队列加大只能吸收突发，不能解决持续到达快于处理。新队列改小也不等于更快；不定义丢弃或背压策略，只会更早触发暂停。

## 8. GPU 加速不足时的后续选择

| 方案 | 具体实施 | 正确性或工程代价 |
| --- | --- | --- |
| 640×480 推理 | 全部事件按 2/3 坐标映射，仍 15 bins；调整模型尺寸 | 像素量为原来的 4/9，不等于耗时必然为 4/9；空间分布和池化尺度改变 |
| torch.compile | 固定尺寸，封装单步输入和显式 state；首窗 / 正常窗分别预热 | 编译时间、额外内存、图中断；不保证 CUDA 算子本身明显加速 |
| TensorRT FP16 | 导出单步模型，state 作为输入输出，常量插值表固定；保留 PyTorch 回退 | 需核验算子与当前 CUDA / 驱动支持，不能直接装最新版；有数值误差和部署成本 |
| INT8 / 小模型蒸馏 | 收集代表性事件窗口校准或重训 | 验证和训练成本高，不作为此次短期演示首选 |

降低推理尺寸时，浮点光流原单位为“推理网格像素 / 输入窗口”。若还原到 960×720，先空间插值，再把横纵分量各乘 1.5；元数据同时记录源尺寸、推理尺寸、输出尺寸和窗口长度。不能只放大 HSV 彩图当作正确尺度的光流数据。把窗口改为 200 ms 后，单位仍是每个输入窗口；若需要像素/秒，应除以实际窗口秒数，时间近似时同时标注其局限。

compile 与 TensorRT 作为第二选择，不与基础流水化同时大改；当前 model_submit P50 只有约 1.9 ms，所以仅减少 Python 提交开销不能解释或解决约 121 ms 的 GPU 执行时间。[torch.compile](https://docs.pytorch.org/docs/2.14/generated/torch.compile.html)、[TensorRT 性能说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/best-practices.html)

## 9. 实施顺序、验收与撤回

先做 A 定时与参数缓存、B 单次光流下载；时间修复作为真实运行验收前置。随后一次只试一个 GPU 加速配置，再做 CPU / GPU 流水化。ROS 批次间断仍高时实施 C++ 桥。C GUI 通知刷新可独立完成；达到演示需求就停止，不继续堆叠后续引擎或线程。

建议验收目标：原支路在输入正常时接近 10 FPS；若坚持完整 100 ms 窗口，模型有效结果接近 10 窗/秒且所有队列年龄不持续增长，GPU 前向 P95 争取低于 80 ms 留出其他工作余量。演示模式的初始目标可放宽到至少 5 FPS，桥回调到控件提交 P95 低于 300 ms，明确报告跳窗比例。以上是目标，不是保证；100 ms 窗口要做到完整处理，不能用丢掉一半窗口达到“5 FPS 稳定”来冒充通过。

验收保持简短：复用同一个 20 秒 RAW 片段，修改前后各跑一次；有明显不确定性才补一次。每次仅比较所改环节的耗时、有效 FPS、所有队列年龄趋势和序号 / 重置原因。输入时间没有修好时，这种完整链路 FPS 不能用于宣称模型优化收益，可用保存的少量连续有效窗口先核对模型计算。

结构性优化要求同样的事件字段、保留掩码和模型输入；纯流水化保持输出顺序与循环状态。混合精度或缩放允许数值变化，取同一段连续输入，记录灰度误差、浮点光流向量误差及末态误差，并看实际演示图是否闪烁、拖影。误差不可接受即退回 FP32 / 原生尺寸。无需增加长时间矩阵、全面压力测试或新的通用测试平台。

每一项保留一个独立提交或局部配置回退点。配置名在实施时确定，本方案不声称这些开关已经存在。算法精度回退到原生 FP32；流水化回退到原串行 worker；显示回退到原定时器；时间修复回退必须同步重开会话和清空 state，不能在同一序列混用两种时间。
