# 实时性优化方案

> 历史记录：该文对应旧的 100 ms/Python 桥版本。当前修改与真机结果见 [E2FAI 修复与真机短测](E2FAI修复与真机短测.md)。

2026-09-12 · 仅供后续选择 · 本次不执行

## 当前演示版本

本次只移植 E2FAI 算法并接回原 Qt 工程。继续使用 12fe7f9 时间映射、960×720 原生分辨率、100 ms 窗口和全部输入事件。界面显示数量可调，但隐藏画面不会关闭算法。短测能出图；输入时间跳变、ROS 批次间断和模型计算时间仍限制实时性。

按最终要求，不做长期压力验收，也不继续扩展测试框架。以下建议基于已有短测，先后顺序按对演示的实际影响排列，不承诺未经验证的提升幅度。

## 建议顺序

### 1. 先核对时间异常

20 秒 RAW 包头正常推进，解码事件却出现约 4,295 秒的跳变，导致窗口和 ConvGRU 反复重置。应先核对原解码器的参考/子时间字、单位和回绕判断，保留既定映射方法，不直接搬入研究分支的包头插值。

最小验证：截取一个出现跳变的短 RAW 片段，对照时间字与解码输出。若正常片段也出现约 2^32 微秒跳变，支持回绕处理存在问题；若 RAW 自身已异常，则继续查采集端。任何修正都要对照旧过滤保留掩码、窗口跨度和断流重置；不能只证明时间单调。改变事件时间会影响过滤历史，需要单独说明兼容性。

### 2. 查清 ROS 到 Python 的接收损失

短回放中原 Python 和新桥各约占一个逻辑核；桥发现 ROS 事件消息序号间断。回调内数组转换只占部分耗时，尚不能把全部损失归因于这几个循环。

最小验证：用相同短输入比较空 Python 回调与当前回调，再按需测量消息反序列化。只有确认转换或 Python 对象处理是热点，才考虑让新桥使用原生实现或减少一次转换。仍从现有 `/dvs/events` 接收，保持逐事件时间、极性、顺序和完整性；不把模型输入换成另一条时间链路。

### 3. 再处理模型计算预算

四画面短回放中，GPU 前向 P50 约 120.83 ms、P95 约 122.99 ms；100 ms 周期的目标目前没有计算余量。结果转图与打包 P50 另约 23.57 ms。仅改变 GUI 刷新率无法解决这部分时间。

最小验证：固定一小段输入，先只测模型与必要输出转换。若后续确需加速，可单独评估混合精度或减少结果重复转换；前者需要比较灰度、浮点光流及连续 GRU 输出误差，后者要求数值与接口不变。降低分辨率或改变窗口长度会改变任务和光流尺度，应作为演示质量取舍单独决定，不能包装成等价加速。

### 4. 有证据后再决定是否跳过过期窗口

当前只在容量超限时明确暂停，没有自动追赶到最新数据。若计算持续跟不上，未来可考虑按数据年龄限制积压，但必须同时定义跳窗后清理 GRU、窗口缓存及结果会话标识的规则。单纯让 GUI 丢旧图无法消除模型在计算旧输入的问题。

最小验证：一次几秒钟的受控推理停顿，观察恢复后的结果年龄和状态重置。只有明确需要此行为才实施；代价是主动放弃部分输入及时间连续性。不得在 RAW 有状态解码前随意丢包，也不得把无事件时年龄增长误判为积压。

## 暂不优先做的事

- 不默认增加线程或队列。更多缓冲可能只让旧数据积压更久。
- 不优先改画布锁。已有短测的锁等待 P95 约 0.003 ms，证据不支持它是主要限制。
- 不优先提高 GUI 帧率。当前刷新间隔 P95 约 100.72 ms，转图提交 P95 约 2.42 ms，模型与输入链路的问题更明显。
- 不把模型前降噪当作免费加速。它会改变事件分布与模型输入；若以后比较，应独立开关并记录保留率。

## 后续若实施，只做一次小改动

选择一个已经确认的问题，用同一短输入作改动前后对照，报告延迟分位数、结果数量、序号间断、输出正确性及 CPU/GPU 占用。GPU 前向与 CPU 等待存在重叠，不能相加；未经校准的事件年龄不是物理端到端延迟。

一次改动独立保存，撤回时恢复该项代码和配置。时间处理改动额外检查原过滤结果；精度或分辨率改动额外检查浮点光流与图像误差。测试以演示需要为限，不预设长时间测试矩阵。

本次没有执行上述任何优化。已有测试数据、限制及源码定位见《移植后性能测试与瓶颈分析》。
