# E2FAI 修复与真机短测

2026-09-12 · 基线 `12fe7f9` · 仅 Markdown

> 后续变更：一分钟实测后，宿主输入队列默认上限从 32 批调至 64 批，可通过 `E2FAI_QUEUE_BATCHES` 调节；256 MiB 内存上限不变。下文实测仍对应 32 批，64 批仅完成基础检查，尚未真机复测。

**代码修改已完成，C++ 桥的短回放通过；现场高事件量运行仍发生一次模型队列超载，不能把当前版本称为高负载下持续流畅。** 本次未调整队列容量、添加跳窗、降低分辨率、抽样或使用混合精度。

## 修改了什么

- 删除旧质心算法、Python/C++ 软件降噪代码、对应控件及构建入口。`capture_monitor.py` 仅统计 RAW 包、字节、序号间断并负责限时退出，不订阅逐事件数组、不生成算法图。
- GUI 默认显示原始图、E2FAI 灰度和光流，可选择 1–3 幅。相机 ON/OFF、Apply、Save、Load 保留；旧配置忽略软件过滤字段，删除 `algorithm` 画面项，剩余为空时恢复三幅。
- 推理默认 **200 ms、960×720、15-bin、全事件**。半开窗口边界事件进入下一窗；断流阈值独立保持 **超过 300 ms**。
- 浮点光流仍为“推理网格像素／输入窗口”，没有将预测值乘二。默认颜色满量程为 40 像素／200 ms；其他窗长按 200 像素／秒换算，显式 `--flow-max-px` 优先。转换为像素／秒时应除以结果携带的实际窗长。
- ROS 桥替换为独立 C++ 进程，保留 `/dvs/events`、`/nrv_e2fai/result`、`/nrv_e2fai/status`、NEF1 协议及原事件字段。宿主机继续运行同一模型和权重。最终工程不安装 Python 桥，旧桥仅保存在本次对照数据目录。

### 窗口大小为何自行变化

原图像 `QLabel` 使用默认尺寸策略。刷新代码根据当前标签大小生成 Pixmap，再调用 `setPixmap()`；Pixmap 又成为 Qt 布局的尺寸提示，形成图像内容反过来改变布局的反馈。原图、旧算法图先到，模型图后到，因此前两幅先改变大小。缩放采用包含边框的 `view.size()` 还会增加额外尺寸反馈。

修复是在布局建立后对图像标签设置 `QSizePolicy.Ignored`，缩放目标改为 `contentsRect()`。主窗口仍可自由拖动缩放，没有增加固定尺寸。见 [GUI](../ros_ws/src/nrv_demo/scripts/gui.py)。

### 约 4,295 秒跳变为何发生

安装的 Group AER 解码器将重复 sub 时间字也当作时间推进，错误执行 `refTS_++`；随后显式 reference 恢复真实值，一次仅 **227 微秒**的回退又被加上 `2^32` 微秒，形成 **4,294.967069 秒**正跳。

补丁让重复时间字保持幂等，明确区分显式 reference 与省略 reference 时的子时间跨界，采用整数 64 位组合。按已安装编码定义，22-bit reference 的周期是 `2^22 × 1000` 微秒；只有实际边界回卷才累计这一周期，其他回退保留。补丁随 Docker 构建应用，不靠手工改运行中的容器。见 [解码补丁](../docker/patches/group_aer_timestamps.patch)、[适配器](../ros_ws/src/nrv_demo/src/dvs_adapter_nodelet.cpp)。

真实录制前 3 秒的直接解码对照：

|---|---:|---:|
| RAW 包数 | 201 | 201 |
| 事件数 | 2,674,233 | 2,674,233 |
| 大于 300 ms 的正跳 | 9 | 0 |

适配器不再丢弃低于初始时间锚点的事件，真实倒退传给组窗并清空窗口缓存与 GRU；新 Start 建立新会话及锚点。**同一会话发生传感器复位后，固定锚点可能产生固定年龄偏差。** 没有插值、排序或强行让时间连续。真正的长周期硬件回卷未等待实测，边界行为由小型时间字用例验证。

## 测试范围与口径

只做了必要检查、同一段真机 RAW 的两次短回放，以及一次约 30 秒现场运行，没有重复矩阵或长期压力测试。

- 硬件：i5-12600KF、RTX 3060 12 GB；宿主模型环境 PyTorch 2.1.1/CUDA 12.1，容器 ROS Noetic/Qt。两份权重不变，严格匹配加载。
- A/B：同一 `capture01/camera.bag` 前 23 秒，1 倍速；预热 3 秒，统计后 20 秒，各一次。两组均修正时间、删除旧算法、使用 200 ms 和三幅 GUI。包头仅做常量 epoch 平移，载荷、顺序及相对间隔不变。每组都输入 1,575 包、133,369,740 RAW 字节；统计段为 1,374 包、118,862,100 字节。
- A/B 的 GUI 使用 Qt offscreen；现场运行使用实际 X11 窗口。不同场景的事件率不同，现场与回放不能当作性能改动前后对照。
- 测量开启，按批次/窗口记录，按单调时间裁出统计段后重新计算分位数，未平均各周期分位数。GPU 指标使用 CUDA 执行计时；计时同步可能造成扰动，本次没有扩展 ON/OFF 对照。
- “桥回调至 GUI 更新”从最后一个贡献批次进入 ROS 桥回调算起，到 Qt `setPixmap()` 为止，取灰度画面一次，避免把两幅模型图算成两次推理。它不包含完整组窗等待，也不代表传感器到显示器的物理延迟。

必要检查通过：组窗/体素 14 项、worker 10 项、时间字 10 项、GUI 9 项、运行摘要 2 项，以及一个实际 ROS/C++/Python 协议互通检查。互通检查确认原始 13 字节事件记录、整数纳秒、灰度/RGB/`32FC2` 数据、旧会话隔离、错误暂停及关闭行为。没有重跑未改动模型的长测。

## 现场真机：高负载仍失败，但控制可用

现场三幅画面正常出图；约在 GUI 打开后 **8.07 秒**，宿主输入 FIFO 达到 **32 批**，按现有规则暂停推理。此时已生成 24 个结果，接收间断为 0。故障不是 Qt 布局或 Python 桥残留造成的。

- 首会话接收约 **8,360 万事件**；拒收 1 批，停止时清除排队中的约 795 万事件。队列峰值约 100 MiB，是批次数上限先触发，而非 256 MiB 字节上限。
- 现场第 3–19 秒区间包含故障后的暂停，模型图实际刷新率只有 **1.19 FPS**。不能剔除停顿后将它包装成流畅帧率；这一区间成功呈现的 19 个结果，其桥回调至 GUI 更新 P50/P95 为 280.21/367.55 ms。
- 按同一窗口配对，19 个样本中有 **3 个**的“体素构建 + GPU 前向 + 转图打包”超过 200 ms，最大 **237.69 ms**。最慢窗口体素 91.59 ms、GPU 121.97 ms、转图 24.13 ms。这些顺序阶段可相加；未叠加与 GPU 前向重叠的 CPU 等待指标。
- GUI 刷新间隔 P95 100.61 ms；独立 20 ms 心跳最大间隔 67.49 ms。暂停时 3→1→2→3 幅切换正常，Stop/Start 恢复出图；一次 ON 参数修改触发新会话后继续出图。三个会话分别生成 24、10、7 个结果，旧会话结果隔离，关闭后 GPU 进程与通信端口已释放。
- 参数测试使用独立 profile，未修改日常保存配置。后两段包含重启与场景变化，不能用于估计改参数后的性能提升。

现场运行摘要为 **DEGRADED**，明确保留 `queue_overflow`。回放 PASS 不能覆盖这个现场失败。

目前最明确的剩余限制是高事件量时模型支路的处理时间及突发积压。单次短测还不能区分持续容量不足与个别大窗口突发，不能据此默认增大队列。本次已按边界停止实施；没有加入其他优化。
